## Гипотезы, которые проверил и ОТБРОСИЛ (не дефект)
- `buyModules`/`startBuild` мутируют `purchased` по месту — это нормальный
  паттерн домена (все функции домена мутируют переданный черновик), сам по
  себе не баг. Баг — если ВЫЗЫВАЮЩИЙ не скопировал глубоко перед вызовом.
- Лимит склада модулей не распространяется на `purchased` — сознательное
  решение (докстринг `construction.ts`), не дефект.
- `startBuild`: списание сначала из `purchased`, потом из `stock` — арифметика
  проверена руками и тестом, отрицательных остатков и потери товара нет.
- Двухэтапный выбор тир/предмет в `droproller.ts`: pity и анти-стокпайл ОДНОГО
  предмета не двигают вес его тира — уже покрыто тестом
  `droproller.test.ts` («свойство: pity/анти-стокпайл ОДНОГО предмета не
  двигают долю его ТИРА»), перепроверять не стал.
- Floor guarantee для двух строек с общим дефицитным модулем (герметик нужен
  и складу, и жилому блоку): проследил вручную последовательность прибытий —
  вторая стройка не голодает вечно, а получает гарантию на следующем же
  прибытии, где первая уже не годится (её окно только что сброшено). Совпадает
  с тем, что заявляет реестр, пункт 22.
- Стык докупки (И-12) и гарантии (И-11): И-11 корректно учитывает `purchased`
  (через `missingFor`), И-7 (pity/анти-стокпайл) — валовую потребность, не
  вычитая `purchased`. Это ЗАРЕГИСТРИРОВАННОЕ решение (реестр п.19), эффект
  ровно тот, что описан там же (щедрость, не эксплойт: лишний модуль уходит в
  общий склад и используется другими стройками). Не нашёл дополнительного
  вреда сверх задокументированного — не завожу как отдельный дефект.
- `advanceWarehouseAvg`: скачок часов назад — no-op (elapsed<=0), скачок вперёд
  (в т.ч. долгий оффлайн) — alpha=1, среднее становится текущим остатком, это
  и есть задокументированное поведение. Не нашёл поломки.
- Смешанная позиция дрона (часть со склада, часть докупкой): `sendOrder`,
  `releaseReserved`, `discardImpact` — трижды прошёл логику руками, везде
  считается через `stockedIn`/`purchasedIn`, а не через `filled_by`. Класс
  Д-1/Д-18 у дрона не воспроизводится.

## Найдено и доказано (см. `src/state/__tests__/defects-run5.test.ts`)

1. **`startConstruction` мутирует чужой снимок `BuildSlot.purchased`.**
   Копирует стройки мелко (`builds.map(b => ({...b}))`), `purchased` не
   клонируется — та же ловушка, которую сосед `buyModulesFor` явно чинит и
   документирует. `startBuild` внутри вычитает из `build.purchased[id]` по
   месту, и это мутирует объект, на который ссылалась ПРЕДЫДУЩАЯ версия
   состояния. Доказано тестом: снимок `purchased`, снятый до действия, меняет
   значение после него.

2. **Обход проверки `SAVE_VERSION`.** `zustand`-мидлварь считает сейв «другой
   версии» только если `typeof persistedVersion === 'number'`. Конверт с
   `version` строкой или без поля `version` вовсе не уходит в `migrate`
   (который у нас всегда отбрасывает несовпадающую версию) — идёт прямо в
   `merge`. Единственная оставшаяся защита, `isSave`, проверяет только верхний
   уровень ключей, не вложенные структуры (это её осознанный контракт).
   Доказано тестом: конверт с `version: "3"` и конверт вовсе без `version`
   оба принимаются как «свои», хотя должны быть выброшены целиком.

   Отдельно проверил: настоящий сейв версии 2/3 (без `drop_floor_guarantee`/
   `warehouse_avg`, которые появились только в v4) с явным числовым `version`
   отбрасывается корректно — `isSave` ловит его по форме независимо от
   `migrate`. Обход актуален именно для конверта с ПОВРЕЖДЁННЫМ/ОТСУТСТВУЮЩИМ
   полем `version`, а не для нормального падения версии на единицу.
