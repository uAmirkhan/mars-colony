## Шаг 1. Главное: читает ли редактор Unity этот FBX (с текстурой, не серым)

Опасение из задачи подтвердилось: проба оркестратора проверяла обратное
чтение В BLENDER, а не в Unity, и это разные вещи. `model-intake.json`:

`mars-unity/incoming-fit.png` (сохранен, до фикса) — объект белый в
крапинку, форма видна, цвета нет.

ДИАГНОСТИКА (не гадание — бинарный разбор самого FBX):
```
python -c "..." # поиск строк RelativeFilename/FileName/Video в grunt-regolit-4.fbx
```
Нашел: внутри FBX ЕСТЬ валидный `Video`-объект с embedded-media —
`Content` содержит настоящие PNG-байты (сигнатура `\x89PNG\r\n\x1a\n`

Но: `RelativeFilename` внутри — `grunt-regolit-4.fbm\Image_0` (папки
`.fbm` на диске НЕТ, только сам .fbx). Проверил `Assets/Incoming/` после
импорта Unity — там только `grunt-regolit-4.fbx` и `.meta`, никакой
распаковки картинки не произошло.

ПРИЧИНА: встроенный (embedded media) FBX редактор Unity не распаковывает
импортом сам по себе — это отдельный вызов API `ModelImporter.ExtractTextures()`,
а не следствие `materialImportMode`. Без него связь материал->текстура
существует только внутри бинарника, ассета-текстуры в проекте не
появляется, и рендер идет плоским цветом.

ПОЧИНЕНО: `mars-unity/Assets/Editor/ModelIntake.cs`, `PrepareImporters()` —
после `SaveAndReimport()` добавлен вызов
`importer.ExtractTextures(textureDir)` (папка `<имя>_textures` рядом с
моделью) и повторный `SaveAndReimport()`, если извлечение что-то вернуло.
Это ровно "запасной путь" из задачи — текстура едет отдельным файлом
рядом с моделью, только распаковку делает сам редактор по API, а не
Blender при экспорте.

ПЕРЕЗАПУЩЕНО В ФОНЕ той же командой для проверки фикса.

ПЕРВАЯ ПОПЫТКА ФИКСА УПАЛА НА КОМПИЛЯЦИИ: `error CS0029: Cannot implicitly
convert type 'bool' to 'bool[]'` в строке 130. В Unity 6000.0.64f1
`ModelImporter.ExtractTextures(string)` возвращает `bool`, а не `bool[]` (в
API некоторых старых версий было иначе — не угадал сигнатуру, поправил по
факту ошибки компилятора, не по памяти). Поправлено: `bool extracted = ...`.
Перезапущено.

РЕЗУЛЬТАТ ФИКСА С EXTRACTTEXTURES: `ExtractTextures` реально сработал —
появилась папка `Assets/Incoming/grunt-regolit-4_textures/Image_0` (1.92 МБ,
проверил байты — валидный PNG, сигнатура `\x89PNG` на месте). НО отчет
`model-intake.json` все еще пишет `"textures": []`, кадр все еще белый.

ВТОРАЯ ПРИЧИНА (докопался дальше): у извлеченного файла НЕТ РАСШИРЕНИЯ
(`Image_0`, не `Image_0.png`) — `.meta` на него говорит `DefaultImporter`,
а не `TextureImporter`. Ассетная база Unity определяет тип импортера по
расширению файла; без `.png` она не признает его картинкой, и материал
остается без ссылки. Расширение отсутствует, потому что имя датаблока
картинки в Blender после импорта GLB — просто `Image_0` (так называет
импортер glTF), и это же имя без изменений уходит в FBX как имя
embedded-media файла.

ПОЧИНЕНО В ИСТОЧНИКЕ (`design/tools/glb-to-fbx.py`, не в Unity): после
сжатия текстур каждой картинке принудительно выставлен `file_format='PNG'`
и в имя добавлено `.png`, если его не было. Пересобираю FBX заново тем же
файлом и бюджетом (12000/1024) под именем `fbx-12000-1024c`, проверяю
Unity-гейт третий раз.

Пересборка прошла: `Image_0.png 1024x1024, Image_1.png 1024x1024` в логе
Blender (имена теперь с расширением), FBX 2.7 МБ (вес не изменился —
расширение в имени датаблока байты не добавляет). Запускаю
`fit-model.mjs --shoot` третий раз на `fbx-12000-1024c/grunt-regolit-4.fbx`.

РЕЗУЛЬТАТ ТРЕТЬЕЙ ПОПЫТКИ: `ExtractTextures` создал файл, но имя все

1. `RenameExtractedTexturesToPng()` — после `ExtractTextures` файл без
   распознанного расширения переименовывается на диске (`File.Move`,
   старый `.meta` удаляется), чтобы ассетная база завела на него
   `TextureImporter`, а не `DefaultImporter`.
2. `FindExtractedTexture()` — находит распознанную текстуру в папке
   `<имя>_textures` рядом с моделью.
3. `EnsureTextured()` — на самом инстансе в сцене примерки досвязывает
   материалы без `_MainTex`/`_BaseMap` с найденной текстурой напрямую, не
   надеясь на автоматическую эвристику FBX-импортера. Вызывается в
   `ShootIncoming` сразу после инстанцирования, до кадра.

Заодно поправлен отчет `MeasureOne`: `GetDependencies` не всегда видит
вручную досвязанную текстуру, отчет молчал бы "текстур нет" при текстуре
на диске — теперь `textures` включает и найденный извлеченный файл.

ЗАПУЩЕНО В ФОНЕ, четвертая проверка Unity-гейта.

## Шаг 3. Вес сборки: во сколько байт обходится одна добавленная модель

Настоящую витрину (`Colony3D.unity`) строит `SceneBuilder3D.BuildScene()` из
`colony3d-scene.json` — трогать нельзя (зона художника). Чтобы не лезть
туда, написан ОТДЕЛЬНЫЙ новый файл `mars-unity/Assets/Editor/BuildSizeProbe.cs`
(не правит `SceneBuilder3D.cs`, не создает риска столкновения с художником):
собирает одноразовую временную сцену (грунт+свет, опционально одна модель
из `Assets/Incoming`) теми же настройками сжатия WebGL (Brotli и т.д.), что
и `BuildWeb3D`/`BuildScript.BuildWeb`, в отдельную папку, и меряет байты.

Это ОЦЕНКА, не точный вклад в реальную сборку: настоящая сцена делит на
150+ объектов общие шейдеры/рантайм один раз, а изолированная сцена платит
эти накладные расходы заново в обоих замерах — поэтому смотрю на РАЗНИЦУ
(с моделью минус пусто), она должна отсечь этот общий накладной вес.
Работаю дальше по этому файлу и уже готовой модели в `Assets/Incoming`
(грант-regolit-4, 12000 тр. / 1024 текстура, с досвязанным материалом).

Первая попытка сборки упала на компиляции: `error CS0234: The type or
namespace name 'BuildTargetGroup' does not exist in the namespace
'UnityEditor.Build'` — `BuildTargetGroup` лежит прямо в `UnityEditor`, не в
`UnityEditor.Build` (спутал с соседним `NamedBuildTarget`, который как раз
в `UnityEditor.Build`, см. комментарий в `BuildScript.cs`). Поправлено,
перезапущено.

ДОЛЬШЕ ПЯТИ МИНУТ: сборка пустой WebGL-сцены идет на этапе `Link_WebGL_wasm`
(IL2CPP + emscripten линковка нативного кода) — это ожидаемо долгий этап
первой WebGL-сборки в проекте, не зависание (лог `probe-empty.log`
показывает прогресс, `[BUSY Ns]` растет). Не жду молча — пока собираю
батч-инструмент задачи 3 (`design/tools/glb-to-fbx-batch.py`, ниже) и не
запускаю параллельно тяжелые задачи, чтобы не давить память во время
линковки.

## Батч-инструмент: `design/tools/glb-to-fbx-batch.py`

Написан. По одной модели за раз, каждая — ОТДЕЛЬНЫЙ процесс
`blender.exe -b -P glb-to-fbx.py -- ...` через `subprocess.run`
(дожидается завершения перед следующей, не Popen без wait) — то же
требование "по одной, без общей сцены", только на уровне процессов, не
одной Blender-сессии. Без аргумента имен берет пять грунтов по умолчанию.
Пишет `batch-report.md` и `<имя>.blender.log` на каждую модель в
выходную папку. Дефолты — 12000 тр. / 1024 текстура (те же, что и у
`glb-to-fbx.py` после правки).

`python -m py_compile design/tools/glb-to-fbx-batch.py` — синтаксис чист.
Первый прогон (все пять грунтов) — после того как освободится Blender/Unity
память от текущей сборки.

СБОРКА ПУСТОЙ СЦЕНЫ ЗАВЕРШЕНА (заняла в сумме несколько минут — этап
`Link_WebGL_wasm`/IL2CPP + Brotli-сжатие wasm, ожидаемо для первой сборки).
`size-probe.json` (сохранена копия `size-probe-empty.json`):
`"bytes": 5339680` (5.09 МиБ / 5.34 МБ десятичных) — базовый вес пустой
сцены (грунт+свет+камера) этим же конвейером сжатия.

Запускаю вторую сборку — та же сцена + модель grunt-regolit-4 (12000 тр. /
1024 текстура, уже лежит в `Assets/Incoming` с рабочим материалом).

## РЕЗУЛЬТАТ ЗАМЕРА ВЕСА (шаг 3, главный вывод)

`size-probe.json` со включенной моделью: `"bytes": 6024077`.
Без модели: `5339680`. Дельта: **6024077 - 5339680 = 684397 байт ≈ 0.65 МиБ
(0.68 МБ десятичных)** — оценка стоимости ОДНОЙ модели grunt-regolit-4
(12000 тр., текстура 1024x1024, после сжатия Brotli) в этом конвейере
сборки.

Перенос на реальную витрину (`metrics-3d.json`, `build.bytes = 5817391`,
не `metrics.json` — см. правку цитаты координатора выше): пять грунтов
такого же профиля ≈ 5 * 684397 ≈ 3.42 МБ; итог ≈ 5817391 + 3421985 ≈
9.24 МБ. Это ВЫШЕ первого порога 8 МБ (вычет 10, шкала S станет 90 —
порог 80 еще не задет), но заметно НИЖЕ второго порога 15 МБ (вычет 25,
который и был бы фатален). Оценка линейная (5 одинаковых по профилю
моделей) и построена на ОДНОЙ модели — реальный разброс по остальным
четырем грунтам может отличаться, точное число даст только настоящая
сборка витрины с добавленными моделями.

ОГОВОРКА ПО МЕТОДУ (честно, не прячу): это ОЦЕНКА через изолированную
одноразовую сцену (`Assets/Editor/BuildSizeProbe.cs`, новый файл, не
трогает `SceneBuilder3D.cs`/`colony3d-scene.json`), а не точный прогон
настоящей витрины до/после — тот способ потребовал бы править
`colony3d-scene.json` (зона художника, запрещено в задаче). Разница
"с моделью минус пусто" должна отсекать общий вес движка/рантайма,
одинаковый в обеих сборках, но не может учесть то, что настоящая сцена
уже делит шейдеры/общий атлас между 150+ объектами — вставка туда может
стоить дешевле предельных байт, чем в сцене с нуля. Если нужно точное
число — это отдельная задача с реальной сборкой витрины, которую я не
делал, чтобы не тронуть чужую зону файлов.

## Финальный батч, все пять грунтов

ЗАПУЩЕНО В ФОНЕ:
```
python design/tools/glb-to-fbx-batch.py design/models/osmotr/fbx-batch 12000 1024
```
Пять последовательных запусков Blender (не одна сцена), 12000 тр. / 1024
текстура — те же настройки, что подтверждены Unity-гейтом на
grunt-regolit-4. Каждая модель — свой лог, кадры и общий `batch-report.md`
в `design/models/osmotr/fbx-batch/`.

ПЕРВАЯ ПОПЫТКА УПАЛА: `UnicodeDecodeError` на кириллице. Причина —
`subprocess.run(..., text=True)` декодирует поток дочернего процесса
кодировкой консоли Windows (cp1251), а Blender печатает по-русски в UTF-8
("треугольников" и т.п.) — падает на первом же непредставимом в cp1251
байте. Побочный эффект: `proc.stdout` после сбоя стал `None`, и запись
лога упала второй ошибкой (`TypeError`). ПОЧИНЕНО: читаю поток БАЙТАМИ
(`capture_output=True` без `text=True`) и декодирую сам explicit'но как
`utf-8` с `errors='replace'`. Первая модель (grunt-regolit-2) успела
полностью обработаться до сбоя — файлы валидны, оставлены, батч
идемпотентен, перезапуск их просто перезапишет тем же результатом.

ПЕРЕЗАПУЩЕНО В ФОНЕ той же командой.
