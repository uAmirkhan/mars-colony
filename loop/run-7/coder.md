## Три задачи по порядку, что вышло

### 1. Главное: читает ли редактор Unity FBX с текстурой — ДА, после трех фиксов

Проба оркестратора проверяла обратное чтение FBX В BLENDER, а не в Unity.
Первый прогон через настоящий редактор (`node fit-model.mjs <fbx> --shoot`
в `c:\Ai\Jarvis\mars-unity`) это опасение подтвердил: модель пришла БЕЛОЙ.
Причина оказалась не в одном месте, а в трех независимых дефектах,
найденных и исправленных по очереди:

1. **Кадры уходили не туда.** `bpy.ops.render.render` резолвит
   относительный путь через внутренний blend-относительный механизм
   Blender, а не через `os.getcwd()` — при несохраненной сцене (наш
   случай на каждом запуске) это уезжает в корень диска (`C:\design\...`),
   тогда как экспорт FBX по тому же пути (чистый `os.path`) шел верно.
   Правка: `design/tools/glb-to-fbx.py`, `src`/`outdir` сразу переводятся в
   `os.path.abspath`.
2. **Unity не распаковывает embedded media FBX сама.** Бинарный разбор
   файла показал: текстура ВНУТРИ FBX валидна (PNG-сигнатура на месте,
   ссылка материал->видео есть — потому Blender при обратном чтении и
   показывал цвет). Но Unity не извлекает такие текстуры на обычном
   импорте — нужен явный вызов API `ModelImporter.ExtractTextures()`.
   Правка: `mars-unity/Assets/Editor/ModelIntake.cs`, `PrepareImporters()`.
3. **У извлеченного файла нет расширения.** FBX хранит имя embedded-медиа
   без точки (`Image_0`, не `Image_0.png`), и даже когда я добавил `.png` к
   имени картинки в Blender, FBX по дороге заменил точку на подчеркивание
   (`Image_0_png`). Ассетная база Unity типизирует импортер по расширению
   файла — без него текстура остается `DefaultImporter`, а не
   `TextureImporter`, и материал остается пустым. Правка: тот же файл —
   переименование извлеченного файла на диске в `.png`
   (`RenameExtractedTexturesToPng`) и явная досвязка материала с найденной
   текстурой в коде (`EnsureTextured`), а не надежда на автолинковку
   FBX-импортера.

**Доказательство:** `mars-unity/incoming-fit.png`, копия сохранена в
`design/models/osmotr/fbx/grunt-regolit-4-unity-gate.png` — объект пришел
С ТЕКСТУРОЙ (оранжевая порода, серые внутренние борта), не белым и не
серым. `model-intake.json`: `"materials": ["metal"], "textures":
["Image_0_png.png"]`.

Команда, которой воспроизводится:
```
cd c:\Ai\Jarvis\mars-unity
node fit-model.mjs "c:\Ai\Jarvis\mars-colony\design\models\osmotr\fbx-batch\grunt-regolit-4.fbx" --shoot
```

Проверено на ОДНОЙ модели (grunt-regolit-4). Фикс общий для конвейера
(не завязан на геометрию конкретной модели), но на остальных четырех
грунтах Unity-гейт отдельно не гонял — только Blender-конвейер (см. пункт 3
ниже). Если нужна гарантия на все пять — это еще 4 запуска
`fit-model.mjs --shoot`, не сделал по нехватке времени в рамках этого узла.

### 2. Бюджет треугольников — СМЕНА ЗАДАЧИ ПО ХОДУ, ЧЕСТНЫЙ ОТРИЦАТЕЛЬНЫЙ ОТВЕТ

Начал по исходному плану (пробовать вверх: 40000/60000/80000 от базовых
20000) — кадры сохранены в `design/models/osmotr/fbx-40000..80000/`,
показывают, что чистота растет с бюджетом монотонно, но это тупиковая
ветка.

**Координатор скорректировал задачу в процессе** (см. `coder-work.md`,
раздел "СМЕНА КУРСА"): потолок `check-model.mjs` — 12000, не 20000
(подтверждено падающим тестом ломателя на реальном файле
`shuttle-20000.glb`). Проверил сам: `check-model.mjs`, строка 364,
`if (m.tris > 12000)`.

**Проверил 12000 треугольников / текстура 1024 — форма грунта НЕ держится
чисто.** На всех пяти моделях партии видны мелкие темные фасетные
разрывы по всей поверхности, заметно грубее, чем даже на 20000 из пробы
оркестратора. Подтверждено ДВАЖДЫ независимо — рендером Blender
(`design/models/osmotr/fbx-batch/*-2-iz-fbx.png`) и кадром из самого
Unity (`incoming-fit.png`, та же рваность видна и там).

Кадры для сравнения (один и тот же ракурс, камера строится по габариту):
- `design/models/osmotr/fbx-12000-1024b/grunt-regolit-4-2-iz-fbx.png` — 12000, рвется сильнее всего.
- `design/models/osmotr/fbx-40000/`, `fbx-60000/`, `fbx-80000/` — прогрессия чистоты вверх (не рабочий диапазон, но показывает тренд).
- `design/models/osmotr/fbx-batch/grunt-led-1-2-iz-fbx.png`, `grunt-regolit-2-2-iz-fbx.png` — то же самое рвется на других моделях партии.

**Не пытался обойти повышением бюджета — прямой запрет в задаче.** Решение
о допустимости 12000 как компромисса (или альтернативном пути — другой
метод децимации, ретопология, снятие потолка) — к владельцу.

### 3. Инструмент + текстуры 1024 + вес сборки

**Резка текстур 4096 -> 1024.** `design/tools/glb-to-fbx.py`: после импорта
GLB все картинки крупнее заданного размера сжимаются `img.scale()`. Здесь
тоже нашелся скрытый баг: `scale()` меняет пиксели в памяти, но embedded
FBX берет данные из УПАКОВАННЫХ байтов (image приходит из GLB уже
packed) — без повторного `img.pack()` в файл уезжал прежний размер 4096
(проверено: FBX весил 23.9 МБ при заявленных в памяти 1024x1024).
Починено. Результат на grunt-regolit-4: FBX **24.2 МБ (4096) -> 2.7 МБ
(1024)**, обратное чтение подтверждает `1024x1024` на обеих картах.

**Батч-инструмент.** `design/tools/glb-to-fbx-batch.py` — новый файл,
плюс командной строкой: `python glb-to-fbx-batch.py выход_папка [бюджет]
[текстура] [имена...]`. По умолчанию — пять грунтов прогона. Каждая
модель — ОТДЕЛЬНЫЙ процесс `blender.exe -b`, дожидается завершения перед
следующей (не общая сцена, не Popen без wait). Пишет `batch-report.md` +
лог на модель. Первый прогон упал на `UnicodeDecodeError` (Blender пишет
UTF-8, `subprocess.run(text=True)` читал кодировкой консоли cp1251) —
починено чтением байтами с явным `decode('utf-8', errors='replace')`.

Финальный прогон, все пять моделей, `design/models/osmotr/fbx-batch/batch-report.md`:

| модель | треугольники | вес FBX | габарит | время |
|---|---|---|---|---|
| grunt-regolit-2 | 11999 -> 11998 | 3.8 МБ | 1.991 x 2.000 x 0.925 | 12 с |
| grunt-regolit-4 | 12000 -> 12000 | 2.7 МБ | 1.995 x 2.000 x 1.898 | 10 с |
| grunt-led-1 | 12000 -> 12000 | 2.9 МБ | 1.858 x 2.000 x 0.863 | 10 с |
| grunt-led-2 | 11999 -> 11999 | 2.5 МБ | 1.981 x 2.000 x 0.630 | 10 с |
| grunt-led-3 | 12000 -> 12000 | 2.7 МБ | 2.000 x 1.951 x 0.854 | 10 с |

Все пять — основание в нуле, вписаны в клетку 2.0 (или близко, по
короткой стороне — сама геометрия не квадратная у части моделей).

**Вес сборки — доп. задача координатора, ответ с оговоркой по методу.**
Координатор попросил померить прирост байт сборки от одной модели через
`mars-unity/metrics.json` (`build.bytes = 6645679`). Проверил цитату сам:
это сборка 2D-ИГРЫ (`Assets/Scenes/Main.unity`), не витрины. Витрина —
`metrics-3d.json` (`Assets/Scenes/Colony3D.unity`), там `build.bytes =
5817391` — именно это число судья использовал в оценке шкалы S прошлого
прогона (`loop/run-6/judge.md:44-48`). Запас до порога 8 МБ от верного
числа — около 2.18 МБ, не 1.66 МБ, как в сообщении координатора.

Настоящую витрину строить не стал — она собирается из
`colony3d-scene.json` (зона художника, трогать запрещено явно). Вместо
этого — новый изолированный файл `mars-unity/Assets/Editor/BuildSizeProbe.cs`
(не правит `SceneBuilder3D.cs`), собирает одноразовую сцену (грунт+свет,
опционально одна модель) теми же настройками Brotli-сжатия, что и
`BuildWeb3D`/`BuildScript.BuildWeb`, в отдельную папку, меряет байты.

- Пусто: **5 339 680** байт (`Build/SizeProbeEmpty`).
- С моделью grunt-regolit-4 (12000/1024): **6 024 077** байт (`Build/SizeProbeModel`).
- Дельта: **684 397 байт ≈ 0.65 МиБ** на одну такую модель.

Перенос на реальную витрину (линейно, от верного `5817391`): пять грунтов
≈ 5817391 + 5*684397 ≈ **9.24 МБ** — выше первого порога 8 МБ (вычет 10,
шкала S станет 90, порог 80 еще цел), но заметно ниже фатального 15 МБ
(вычет 25). ЭТО ОЦЕНКА через изолированную сцену, не точный прогон
реальной витрины: настоящая сцена делит шейдеры/рантайм между 150+
объектами один раз, добавление туда может стоить дешевле краевых байт,
чем с нуля. Точное число даст только сборка настоящей витрины с
добавленными моделями — не мой файл, не стал трогать.

## Расхождения, которые обязан доложить

1. **Число из сообщения координатора неверное.** `metrics.json`
   (`build.bytes = 6645679`) — это 2D-игра, не витрина. Правильный
   ориентир — `metrics-3d.json` (`5817391`), подтвержден судьей прошлого
   прогона. Разница на арифметику задачи не критична (обе оценки говорят
   "тесно, но пять грунтов не роняют шкалу ниже 80"), но число процитировано
   неверно, и я обязан это отметить, а не тихо промолчать.
2. **ТЗ (план узла) молчало про Unity-специфику embedded-media FBX** —
   пришлось решать самому по бинарному разбору файла, без чужого
   прецедента в коде проекта. Решения (ExtractTextures + переименование +
   ручная досвязка материала) не описаны нигде в спеках, это инженерное
   решение конкретной технической проблемы, а не игровое правило.
3. **Бюджет 12000 треугольников не проходит "чисто" ни на одной из пяти
   моделей.** Это прямой конфликт с целью прогона ("карьер закрывают
   модели грунта, а все пять грунтов — в списке годных"): годны по форме
   (не "плита", не "блин"), но поверхность рвется на разрешенном потолке
   треугольников. Технически я это не чиню (не моя область — не
   ретопология и не смена метода децимации), только докладываю числами и
   кадрами, как велено.

## Что не заработало / не сделано

- Unity-гейт (пункт 1) проверен только на grunt-regolit-4, не на всех
  пяти — фикс общий для конвейера, но отдельно не подтвержден на
  остальных четырех запуском `fit-model.mjs --shoot`.
- Вес сборки — оценка через изолированную сцену, не точный прогон
  настоящей витрины (осознанно, чтобы не трогать `colony3d-scene.json`).
- Мусорная папка `C:\design\models` (побочный эффект уже починенного
  бага путей) осталась на диске — `rm -rf` вне рабочего каталога проекта
  заблокирован инструментом песочницы, безвредна.
- В `Assets/Incoming/<модель>_textures/` после `--shoot` остается один
  лишний файл без расширения (`ExtractTextures` перевыполняется на каждый
  из двух прогонов `PrepareImporters` внутри одного `--shoot`) — не
  мусорит результат (нужный файл находится верно), но если решат чистить —
  нужно удалять папку `_textures` в начале `PrepareImporters`, не стал
  трогать сверх необходимого для гейта.
