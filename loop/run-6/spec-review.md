### 2.2 И-13 (изоляция дефицита) — контракт лока сверен дословно

`domain/deficitlock.ts` реализует ровно четыре элемента канона 1.5: тип `DeficitLock` (без `player_id` — задокументированное упрощение, домен и так на одного игрока), `isDeficitLockedByOtherMechanic`, `registerDeficitLock` (upsert-if-absent — живой чужой лок не трогает, живой свой не трогает, истекший перезаписывает), `releaseDeficitLock` (снимает только лок своей механики). TTL: `DEFICIT_LOCK_TTL_MAX = 24*60*60` и `DEFICIT_LOCK_TTL = DEFICIT_LOCK_TTL_MAX` (`config/economy.ts:295,305`) совпадают с каноном («потолок 24ч», «дрон-заказы висят без таймера»). Терминальные события: `sendOrderAt`/`discardOrderAt` (дрон, `gameStore.ts:949,978`) и `depart` (шаттл, `shuttle.ts:577-586`, отправка — терминальное событие, канон явно перечисляет `depart` отдельно от `deliver/discard`). Проводка через стор проверена отдельным набором тестов уровня стора (`state/__tests__/deficit-lock-store.test.ts`), не только доменных — ровно то требование, которое задание выделило отдельно.

**Найдена небольшая непоследовательность проводки.** `state/gameStore.ts:987-999` (`refreshSlotNow`) вызывает `makeOrder(slot_idx, s.now)` (`:998`), которая по докстрингу самого стора (`gameStore.ts:544-551`) обязана сопровождаться новой ссылкой: «Вызывающий обязан после этого прогнать `set({ deficit_locks: {...} })`». Но `set()` на строке 999 несет только `{ orders, isotopes: s.isotopes - price }`, без `deficit_locks`. Все остальные вызывающие `makeOrder`/`makeTrip` (`tick:712-726`, `sendOrderAt:954-959`, `discardOrderAt:979`) этому правилу следуют. Поскольку `registerDeficitLock` мутирует объект `s.deficit_locks` по месту (не создавая новый), сами данные лока не теряются — `get().deficit_locks` их видит. Единственное следствие пропуска — отсутствие новой идентичности объекта для подписчиков стора; ни один компонент UI на `deficit_locks` не подписан, поэтому наблюдаемого игроку эффекта нет. Не найдено ни одним тестом (гейт зеленый), поскольку тесты читают состояние через `get()`, а не через сравнение ссылок. Серьезность низкая — это нарушение собственного задокументированного контракта проводки, а не потеря данных, но именно такие места стали причиной находок Д-1/Д-18 в прошлых прогонах, поэтому стоит отметить явно.

### 2.4 Главная находка: `rebalanceForAchievability` не знает о `deficit_locks` — И-10 и И-13 конфликтуют на практике

Сигнатура функции (`shuttle.ts:286-291`):
```
export function rebalanceForAchievability(
  slots: ShuttleSlot[],
  warehouse: WarehouseState,
  budget: number,
  available_goods: GoodId[],
): ShuttleSlot[] {
```
не принимает `deficit_locks` вообще. Когда рибаланс доходит до ветки замены товара (не может резать количество ниже пола — `:322-335`), кандидат на замену выбирается только по скорости производства (`GOODS[a].prod_time_sec - GOODS[b].prod_time_sec`) — без проверки, залочен ли этот товар другой механикой.

Я самостоятельно прогнал непрокоммиченный файл `src/domain/__tests__/defects-run6.test.ts` (`npx vitest run` — 3 из 3 упавших) и воспроизвел это независимо, читая `shuttle.ts` и `deficitlock.ts` напрямую:

- **На уровне самой функции.** Дрон держит лок на `mushroom_soup`. Отсек с `jumpsuit` (уже на полу количества, резать больше нечем) отправляется в `rebalanceForAchievability(slots, w, 5, ['jumpsuit', 'mushroom_soup'])`. Единственный кандидат на замену в пуле — сам залоченный `mushroom_soup`, и функция его берет: `result[0].good_id === 'mushroom_soup'`, при этом `mushroom_soup` в получившемся количестве сам остается не легким (`productionTimeMinutes(...) > EASY_PRODUCE_MAX_MIN.shuttle`) — то есть настоящей дефицитной позицией, а не безобидной заменой.
- **На уровне полного `generateTrip`.** Тот же сценарий целиком: рейс шаттла получает отсек с товаром, уже дефицитно залоченным дроном (`generateTrip` возвращает `trip.slots`, где есть `mushroom_soup` с `productionTimeMinutes > EASY_PRODUCE_MAX_MIN`). Финальный цикл регистрации (`shuttle.ts:509-519`) вызывает `registerDeficitLock` для этого отсека, но `registerDeficitLock` — upsert-if-absent (канон 1.5, `DO NOTHING` при конфликте): владение локом остается за дроном (`locks.mushroom_soup?.locked_by_mechanic === 'drone'`), регистрация для шаттла молча не срабатывает. При этом сам отсек никуда не девается из рейса — рибаланс уже выбрал этот товар до попытки регистрации, и попытка регистрации ничего не откатывает. В итоге игрок видит две одновременные просьбы (дрон-заказ и рейс шаттла) произвести один и тот же дефицитный товар — ровно тот сценарий, для предотвращения которого написан И-13.

Это прямое расхождение с формулировкой канона: «Товар, уже держащий дефицитную позицию у ДРУГОЙ механики, не может стать дефицитной позицией и здесь» (докстринг самого кода, `shuttle.ts:404-408`, дословно повторяющий идею канона 1.3) — но это правило проверяется только в основном цикле подбора кандидатов (`shuttle.ts:409-415`), а не в отдельной функции `rebalanceForAchievability`, которая обрабатывает отсеки уже после основного цикла и способна заново ввести залоченный товар.

**Важная оговорка про источник дефекта.** Псевдокод канона 1.4 для `rebalanceForAchievability` (`tz-common-systems-mars.md:266-282`) сам не принимает `deficit_locks` и не проверяет локи при вызове `fastestProducibleGood(pool, excluding=positions.goods, player, config)` — то есть эта дыра присутствует уже в псевдокоде спецификации, а не только в реализации. Приоритет фолбэков канона 1.3 («достижимость > покрытие > анти-повтор > изоляция дефицита») объясняет, что фолбэк изоляции «тривиален» и происходит «в цикле выше» — но этот текст описывает только основной цикл подбора, не рибаланс достижимости, и канон нигде явно не разрешает рибалансу достижимости повторно вводить залоченный товар. Это одновременно находка по коду (функция не принимает нужный вход, хотя ее вызывающий уже знает про `deficit_locks`) и находка по спеке (канон молчит про пересечение этих двух конкретных механизмов, введенных в разных разделах одного документа). Серьезность средняя-высокая: сценарий не экзотический — он воспроизводится ровно там, где игра регулярно сужает пул товаров (низкие уровни, ранние брекеты — тот же класс тесноты пула, что уже стал причиной находок реестра 12 и 24).

### 2.5 Второстепенное наблюдение: TTL-потолок лока против «вечно висящего» заказа дрона — поведение соответствует канону, не дефект

Тот же непрокоммиченный файл показывает третий сценарий: дрон-заказ с дефицитной позицией `jumpsuit`, ни разу не терминированный (не отправлен, не выброшен) за `DEFICIT_LOCK_TTL_MAX` (24 игровых часа) — лок истекает по TTL, и шаттл получает право забрать `jumpsuit` в свой собственный дефицит, хотя дрон-заказ формально все еще активен. Это выглядит как нарушение И-13 на уровне намерения, но сам канон 1.5 прямо объявляет этот компромисс сознательным: «дрон-заказы могут висеть без таймера сколь угодно долго... поэтому лок все равно ограничен потолком `DEFICIT_LOCK_TTL_MAX` (24ч), чтобы забытый заказ дрона не блокировал шаттл/лайнер навсегда» (`tz-common-systems-mars.md:304`). Код (`economy.ts:290-305`, докстринг дословно цитирует эту же мысль) реализует канон так, как он написан. Отмечаю это не как расхождение, а как подтверждение: канон сам допускает эту дыру для абандон-сценария, а «абандон» и «просто давно висит» канон не различает — это заранее принятое ограничение механизма, а не находка кода.

### 2.6 Аналитика И-13/И-10 (канон 1.8) — не реализована, отдельно от основного контракта 1.5
